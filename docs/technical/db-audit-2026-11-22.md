Changes from the proposals below, found while implementing the index PR:

- **`Sound` newest-public feed index is a plain composite, not partial.** Prisma binds enum filters as `CAST($n::text AS "channel"."SoundStatus")`, which Postgres does not constant-fold, so it can never prove a `WHERE "status" = 'READY'` index predicate. `@@index([isPublic, status, releasedAt(sort: Desc)])` (`Sound_isPublic_status_releasedAt_idx`) serves the same queries and lives in `schema.prisma`.
- **Trigram indexes are in `schema.prisma`** (`@@index([title(ops: raw("gin_trgm_ops"))], type: Gin)` and the `postgresqlExtensions` preview feature declaring `pg_trgm` in `public`), so `prisma db push` test databases get them too. Prisma's `contains` + `mode: 'insensitive'` emits a plain `"col" ILIKE $1`, which a `gin_trgm_ops` index on the bare column serves; no `lower()` expression is needed. Queries shorter than 3 characters have no trigram and still scan.
- **Tag search** uses `"channel"."lower_tags"("tags") @> ARRAY[lower($1)]` and the GIN expression index `Sound_lower_tags_idx`. Prisma cannot manage functions, so `db:migrate:test` (`prisma db push`) also runs `packages/db/prisma/raw-sql/lower-tags.sql`; `src/migrations-schema.test.ts` checks it matches the migration.
- **Raw-only indexes** (not in `schema.prisma`): `Download_counted_soundId_idx` (partial) and `Sound_lower_tags_idx` (expression). Prisma 5.22 skips partial and expression indexes when diffing, so `migrate dev` / `migrate diff` do not try to drop them (verified; a plain index missing from the schema does show up as a DROP). If a newer Prisma starts generating a DROP for them, delete that line from the generated migration.
- **`CREATE INDEX CONCURRENTLY` under `prisma migrate deploy`** works when it is the only statement in `migration.sql` (comments are fine). With two statements Prisma runs the file as one transaction and Postgres fails with `25001 cannot run inside a transaction block` (verified on Postgres 16, Prisma 5.22). `src/migrations-schema.test.ts` enforces one statement per CONCURRENTLY migration, and schema-qualified `CREATE INDEX ... ON` / `DROP INDEX`.
- If a CONCURRENTLY build fails part-way it leaves an `INVALID` index, and the `IF NOT EXISTS` retry would skip it. Recover with `DROP INDEX CONCURRENTLY "<schema>"."<name>";`, then `prisma migrate resolve --rolled-back <migration>` and deploy again.

## Verified locally: Prisma `_count` and `distinct`

I checked two behaviours against Prisma 5.22 and a throwaway `postgres:16` (2k sounds, 400k listen events). Neither query touched tahti-org data:

1. **`select: { _count: { select: { listenEvents: true } } }` on `findMany`** produces this SQL:
   ```sql
   LEFT JOIN (SELECT "soundId", COUNT(*) FROM "ListenEvent" WHERE 1=1 GROUP BY "soundId") ...
   WHERE "Sound"."id" IN (...) LIMIT 24
   ```
   Postgres pushes the key into the subquery only for a single `id = $1` lookup, as on the track page. For list queries (`IN (...)`, `ORDER BY ... LIMIT`), `EXPLAIN ANALYZE` showed a **Parallel Seq Scan + HashAggregate over the entire `ListenEvent` table**, and the same over `SoundLike` (46 ms at 400k rows; it grows linearly).
   - With `previewFeatures = ["relationJoins"]` and `relationLoadStrategy: 'join'`, the same call becomes a per-row `LEFT JOIN LATERAL (SELECT COUNT(*) ... WHERE t1.id = t3."soundId")`, which is index-backed.
2. **`distinct: ['soundId']` with `take`** produces `SELECT id, soundId FROM ListenEvent WHERE dedupeKey = $1 ORDER BY id OFFSET 0` with no `LIMIT`. Prisma fetches every matching row and de-duplicates them in Node.

## Missing indexes

All SQL is schema-qualified. **Partial and INCLUDE indexes cannot be expressed in Prisma 5.22 `@@index`.** If you add them as raw SQL, `prisma migrate dev` will offer to DROP them in the next generated migration. Remove that statement by hand, and document the convention in `packages/db/README` or an ADR.

`CREATE INDEX CONCURRENTLY` cannot run inside a transaction block. Keep one such statement per migration file, because Postgres runs a multi-statement script as one implicit transaction. Confirm with a staging deploy.

-- Table and index sizes, row estimates
SELECT n.nspname AS schema, c.relname AS table, c.reltuples::bigint AS est_rows,
       pg_size_pretty(pg_table_size(c.oid)) AS table_size,
       pg_size_pretty(pg_indexes_size(c.oid)) AS index_size
FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace
WHERE c.relkind = 'r' AND n.nspname IN ('core','channel','chat','ledger','governance','engagement','fansubs','release','newsletter','venue','media','admin')
ORDER BY pg_total_relation_size(c.oid) DESC LIMIT 30;

-- Unused or rarely used indexes (candidates in the Redundant table)
SELECT s.schemaname, s.relname, s.indexrelname, s.idx_scan,
       pg_size_pretty(pg_relation_size(s.indexrelid)) AS size
FROM pg_stat_user_indexes s JOIN pg_index i ON i.indexrelid = s.indexrelid
WHERE NOT i.indisunique AND s.schemaname <> 'public'
ORDER BY s.idx_scan ASC, pg_relation_size(s.indexrelid) DESC LIMIT 40;

-- Tables read mostly by seq scan
SELECT schemaname, relname, seq_scan, seq_tup_read, idx_scan, n_live_tup,
       round(seq_tup_read::numeric / GREATEST(seq_scan, 1)) AS avg_rows_per_seq
FROM pg_stat_user_tables
WHERE schemaname <> 'public'
ORDER BY seq_tup_read DESC LIMIT 25;

-- Write churn (cost of the 6-7 indexes on Download / ListenSession)
SELECT schemaname, relname, n_tup_ins, n_tup_upd, n_tup_hot_upd, n_tup_del, n_dead_tup, last_autovacuum
FROM pg_stat_user_tables WHERE schemaname IN ('engagement','chat','core') ORDER BY n_tup_ins + n_tup_upd DESC LIMIT 15;

-- Heaviest statements (needs pg_stat_statements; check first)
SELECT extname FROM pg_extension WHERE extname = 'pg_stat_statements';
SELECT calls, round(total_exec_time)::bigint AS total_ms, round(mean_exec_time::numeric, 2) AS mean_ms,
       rows, left(regexp_replace(query, '\s+', ' ', 'g'), 220) AS query
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 25;

-- The specific suspects, by text
SELECT calls, round(mean_exec_time::numeric, 2) AS mean_ms, left(query, 200)
FROM pg_stat_statements
WHERE query ILIKE '%aggr_selection%ListenEvent%'      -- Prisma _count full aggregates
   OR query ILIKE '%"ListenEvent"%"dedupeKey" = %'    -- new-to-you
   OR query ILIKE '%FROM "engagement"."ListenSession"%"startedAt" >=%'  -- /metrics
   OR query ILIKE '%unnest("tags")%'                  -- tag search
ORDER BY mean_exec_time DESC;

-- Session / token backlog for the retention sweep
SELECT count(*) FILTER (WHERE "expiresAt" < now()) AS expired, count(*) AS total FROM core."Session";
SELECT count(*) FILTER (WHERE "expiresAt" < now() OR "revokedAt" IS NOT NULL) AS dead, count(*) AS total FROM core."RefreshToken";

-- Plan checks (EXPLAIN only, does not execute)
EXPLAIN SELECT "soundId" FROM engagement."ListenEvent" WHERE "dedupeKey" = 'user:x' ORDER BY "playedAt" DESC LIMIT 200;

Decisions these numbers gate:

- **ListenSession and Download indexes:** drop `(source, startedAt)`, `(countryCode, startedAt)` and `Download(countedAt)` only if `idx_scan` is about 0 since the last stats reset.
- **Event retention:** the rollup-and-prune proposals depend on the actual sizes of `ListenEvent`, `ListenSession` and `Download`.
- **Trigram indexes:** they pay off only if `User` and `Sound` are beyond a few thousand rows. Below that, seq scans are fine and only the `/metrics` and `_count` fixes matter.
