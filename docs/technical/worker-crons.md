# Worker repeatable cron jobs

BullMQ repeatable jobs are declared in **`packages/shared/src/worker-cron-jobs.ts`** (`WORKER_CRON_JOBS` — single manifest for workers, API admin, and runbooks). The stack's single `cron-runner` service registers that manifest; worker replicas only execute the resulting jobs. Every execution is persisted in `CronRun` with outcome, returned JSON summary, error, and duration, visible at `/admin/crons`.

**Dispatcher jobs** (`subTasks` in the manifest) run several related tasks in one tick, in order. Each sub-task is logged to `CronRun` under its own name, so `/admin/crons` still shows per-task history. A failing task is recorded and does not stop the ones after it; the dispatcher does not rethrow, so BullMQ never re-runs tasks that already succeeded (e.g. payouts). Sub-tasks of one dispatcher must belong to the same worker lane. Ordered dispatchers (daily/weekly) run tasks sequentially; the per-minute and per-10-minute ticks run them in parallel (`runCronTasks(..., { parallel: true })`) so one slow task, e.g. `channel-watchdog` waiting on the orchestrator, cannot delay `radio-slot-switchover`.

To add a cron: extend `WORKER_CRON_JOBS` in `packages/shared/src/worker-cron-jobs.ts`, implement the handler in `apps/worker/src/jobs/`, wire the job name in the worker dispatch in `index.ts`, and return a compact summary object so the Admin cron log records a useful result.

### Auth row retention (`auth-row-retention`)

On the request path, rows are deleted only by logout, revocation, or presenting an expired session again; rows nobody presents again are left to this sweep. It deletes 5,000 rows per `DELETE` by primary key, looping until a batch comes back short. The grace period is `AUTH_ROW_GRACE_DAYS` (whole days, default 7); `cutoff = now - grace`. Result: `{ sessions, refreshTokens, batches, graceDays }`.

- **`RefreshToken`:** a token stops working at `revokedAt` (rotated or revoked) or `expiresAt`, whichever is first. A token is deleted only when **every token in its family** stopped working before the cutoff. Reuse detection (`rotateRefreshToken`) needs a family's retired tokens while any token in it can still mint: replaying a retired token is what revokes the live tip and deletes the session. A family is bounded by `REFRESH_TOKEN_ABSOLUTE_CAP_SEC` (default 365 days), so its rows go at most that plus the grace period after login.
- **`Session`:** deleted when `expiresAt` is before the cutoff **and** no refresh token on it is unrevoked with `expiresAt` at or after the cutoff. There is no revoked state (revocation deletes the row). A refresh pushes `Session.expiresAt` forward without checking it, and refresh tokens (60 days) outlive sessions (30 days), so an expired session with a usable refresh token can still come back. Deleting a session cascades to its remaining (dead) refresh tokens; the sweep runs the token rule first so those are mostly already counted.

Neither table has an `expiresAt` index, so each batch scans the table; `Session(expiresAt)` and `RefreshToken(expiresAt)` indexes would serve it.

Host-level backups (Postgres, MinIO) are **not** in BullMQ — use `scripts/backup.sh` and `/etc/cron.d/tahti-backup` (see `ops/RUNBOOK.md`).
